# Draft purchase plan in the existing purchase aggregate

> Proposed design, 2026-11-06. Approved for documentation only; **not implemented**. T2: schema, monetary data, public API, and write-policy changes. Human review is required before implementation/merge. The existing purchase and allocation contracts remain authoritative until then.

## Outcome and decisions

Record why each item is needed while assembling a purchase draft. The owner chose to use the existing `Purchase(status="draft")`, **not** a separate plan entity. Supplier, purchase date, and purchase total stay required even for a draft. A draft can be edited, and its lines can be added, edited, or removed; lines with resource allocations cannot be edited or removed. **After the approved contract cutover**, every new line must have a purpose, including lines added to an order through existing creation routes. During the temporary compatibility phase, old clients can still create lines without the new metadata; measure and retire this exception at cutover. Legacy lines retain an unknown purpose rather than deriving it from `notes`.

The owner chose to retain the current procurement API audience for this design: authenticated readers and API-key readers; coordinator/admin and API-key writers. This is **not** department isolation or an endorsement for exposing financial reports. The later budget/access-control redesign (trusted department scope, separate finance role, tightening existing global finance APIs) remains a separate breaking rollout. The owner explicitly requested design only in this session; no migration, endpoint, permission change, or production action is authorized by this document.

## Existing behavior and scope boundary

`Purchase` requires `supplier`, `purchase_date`, and `total_amount`; its statuses are `draft`, `ordered`, `received`, `cancelled`. `PurchaseItem` has `description`, `quantity`, `unit_price`, and `notes`; it has no `purpose`, `priority`, or `unit` today. The item also has no stored line total; `quantity * unit_price` is the derived line value. Existing endpoints list/create purchases and items and list/create allocations and transactions; there is no draft/detail/PATCH/DELETE or order-placement action. See [purchase model](../../../models/procurement/purchase.py), [routes](../api/urls.py), and [commands](../application/commands.py).

A draft is an **estimate/intent**, not an approved department budget, a reserved amount, invoice-recognized expense, resource allocation, or settled payment. This change creates none of those records and does not implement the future budget warning at order placement. Existing `PurchaseTransaction` is a settled cash event, not a planned expense. Do not add draft estimates to actual-spend or cash-flow totals. A commercial `Purchase` already contributes to existing purchase lists; adding item metadata must not silently alter their report formulas.

## Proposed fields and contract

| Field | Draft/new-row rule | Persistence and compatibility |
| --- | --- | --- |
| `PurchaseItem.purpose` | Required, non-whitespace text for each **new** item regardless of purchase status; propose maximum 2,000 characters. | Add nullable `TextField` with `null=True, blank=True` temporarily for historical rows. API reads expose `null` for legacy unknown values. Do not copy from `notes` or set a misleading default. A later backfill/non-null constraint requires its own decision. |
| Per-item remark | Optional free-text explanation, proposed maximum 2,000 characters; distinct from the purchasing justification in `purpose`. | **Proposed contract choice:** reuse the existing `notes` column and public `notes` field as the remark; the UI may label it “Remark”. There is no public `remark` field in this proposal. If clients require the literal key `remark`, approve a documented alias/deprecation plan first; do not add a second column that can diverge from `notes`. |
| `PurchaseItem.priority` | Proposed explicit enum `low`, `normal`, `high`, `urgent`; **explicitly required on every new item** after contract cutover. | Add nullable `CharField` for legacy rows with a named database check on allowed values when present. No implicit default for new rows; legacy `null` means unknown, not `normal`. Do not silently reorder invoices or reserve funds based on priority. |
| `PurchaseItem.unit` | Required unit label for new rows, e.g. `piece`, `pack`, or `license`; propose maximum 32 characters. | New nullable column for legacy rows; a free-text input is a proposal pending a controlled unit catalog decision. Do not infer a unit from description. |
| `PurchaseItem.quantity` | Required positive integer on **both** purchase-with-items and add-item create endpoints after cutover. | Already persisted with a positive database check. Existing default 1 is a legacy contract to retain during expansion only; make omission a 422 in both endpoints **only after** the breaking-change approval and client migration. No fractional quantities in this slice. |
| `PurchaseItem.unit_price` | Keep required non-negative amount in the purchase currency; zero can mean the estimate is not yet known, **not** a free order. | Already persisted `Decimal(14,2)` with a nonnegative database check. No new per-item currency. |

Unresolved owner sign-off: the exact priority vocabulary, permissible units (free text vs controlled catalog), text limits, and whether the public field must literally be named `remark` rather than the proposed reuse of `notes`. The requirement to capture `unit` at new item creation is retained; any relaxation requires a separate owner decision. If a dedicated persisted `remark` is required in addition to `notes`, define its distinct meaning and legacy mapping before migration. Do not add speculative columns to solve undecided requirements.

`Purchase.total_amount` remains a separately entered commercial/estimated total in the current contract; `is_balanced` compares it with line values but is not currently a write invariant. Show both total and line-derived total in a future draft detail **only if** their semantics are named explicitly; do not silently recompute or overwrite `total_amount`. Invoice-date recognition, partial invoices, and frozen FX for a future budget design are **not verified as approved repository decisions** and are outside this draft's scope.

## Proposed HTTP workflow (all slashless; not live)

| Method and path | Intended command/query | Preconditions |
| --- | --- | --- |
| `POST /api/labs/purchases` | Existing purchase creation extended with nested item metadata. | Preserve required header fields; each supplied new item needs purpose, priority, unit, quantity, unit price under the approved contract. A purchase with zero items may remain a draft. |
| `GET /api/labs/purchases/{purchase_id}` | Detail selector; include exact parent fields, version, and links/counts (not unbounded inline collections). | Same access audience as existing purchase list, pending separate security rollout. |
| `PATCH /api/labs/purchases/{purchase_id}` | Edit supplier, purchase date, order number, currency, total, and notes. | Draft only; no status change via PATCH; strong `If-Match`, parent version; changes with payment/allocation implications need explicit rules before implementation. |
| Existing `GET/POST /api/labs/purchases/{purchase_id}/items` | List/create lines; capture per-item purpose, priority, unit, and existing fields. | Existing GET behavior retained; making purpose/priority/unit/explicit quantity required for POST is breaking and requires client cutover. |
| `GET/PATCH/DELETE /api/labs/purchases/{purchase_id}/items/{item_id}` | Detail/update/remove one line. | Item must belong to parent. Edit/delete only in draft, only if no allocations. `If-Match` for PATCH/DELETE; DELETE returns 204. |

Items added as part of draft editing do not make an order “placed”: there is no implemented placement transition. Do not repurpose `POST /purchases` to place an order or allow arbitrary writable `status` on the new PATCH. Existing purchase creation can currently accept a status supplied to its *command* even though the HTTP serializer exposes status read-only; status-transition rules need their own documented API/design review.

Input serializers and output serializers must be separate for new operations, explicitly allowlist fields, and reject unknown/read-only inputs. Output must keep current monetary response shapes on old routes until an approved version/compatibility plan. List results use the standard bounded paginator, order by a unique `id` tie-breaker, and avoid per-line relation queries. Incorrect parent IDs, missing IDs, and future hidden IDs return the same 404 response. Return normal API error envelopes for 409 state conflicts, 412 stale, 428 missing precondition, and 422 invalid fields; return `Location` on 201.

**Contract classification (VER-2):** additive item response fields/detail and edit routes are non-breaking if old clients ignore unknown response keys; requiring purpose/priority/unit/**explicit quantity** on both existing item-create paths and requiring concurrency headers on any old write route are breaking. Preserve legacy reads/history. Stage new field acceptance first, deploy updated clients, then enable the required-field validation with separately approved cutover. Do not claim that non-production means clients cannot break.

## Write safety and integrity

1. Define one parent-first lock order for *every* draft edit: `Purchase` → relevant `PurchaseItem` rows in primary-key order → resource allocation checks. An existing allocation command locks `PurchaseItem` **before** `Purchase`; refactor that command in the same slice before taking parent-first locks, otherwise concurrent allocation/edit may deadlock. Add PostgreSQL concurrency tests. Avoid lockless check-then-write.
2. Keep each create/update/delete inside one command-owned atomic transaction with explicit actor. Use a version counter on the parent for header edits and list mutation, plus one on a line if line-level ETags are exposed. Compare-and-update or lock-then-check the version so stale edits fail without overwriting anyone else. Replays of conditional PATCH/DELETE either return the original result (stored idempotency contract) or the documented 412/404 outcome; they must not duplicate lines.
3. Under the parent lock, confirm draft status and absence of line allocations for changes to an item. Forbid changing purchase currency if any related allocation, transaction, or other committed financial activity exists; changing the purchase total requires a documented balancing rule before implementation. **Existing** transaction and allocation creation currently have no draft-specific restriction; requiring a clean planning phase on all write paths is a separate behavioral change and must be coordinated with those writers. No deletion of a purchase or its settled history is proposed.
4. DB-enforced: existing item→purchase protected FK, positive quantity and nonnegative unit price. New `priority` enum check enforces vocabulary. `purpose` and `unit` nonblank for **new** rows while historical rows remain null is only application-enforced during expand/backfill; a normal row check cannot distinguish preexisting rows from new rows. “Only draft”, “not allocated”, “header total equals line sum”, and a parent-version check span rows or current workflow state: enforce through cooperating commands and consistent locks; if direct/admin SQL must obey them, design triggers or an immutable snapshot before claiming a database guarantee.
5. New create calls require a defined `Idempotency-Key` scope: **credential + HTTP method + path**, key, and body fingerprint, with a constraint that prevents using the same key under a credential on a different body/path; follow WRT-8 replay, retention, and in-progress behavior. A repeated key/body returns the original status/body; reuse for a different body **or path** returns 422. There is not yet a compliant shared implementation. A key-only request currently has `actor=None`; **never interpret it as unrestricted authority** when adding new commands. An explicitly scoped, auditable machine identity is needed before implementing safe key-backed draft writes.

## Rollout and tests

1. **Design review:** settle the open decisions above, classify the old API client cutover, inspect callers, and review API-key ownership/security. Obtain human approval for any access-control or contract break before merge. No finance visibility is inferred from continued procurement API visibility.
2. **Expand:** add nullable `purpose`/`unit`/`priority` (priority check when present), parent/line version counters, and needed request-idempotency persistence in a new Labs migration. Do not edit applied migrations. Model changes update the [authoritative Labs model document](../../../models/docs/labs-model-architecture.md) in the same *implementation* change; this proposal is not a second model authority. PostgreSQL lock timeouts and concurrent-index tactics depend on measured table size. Reversal of additive schema is only safe if no new data has been written; otherwise retain columns and roll back code first.
3. **Application and API:** accept new metadata, add detail/edit/delete with model-backed selectors, lock-compatible commands and no workflow side effects. Apply per-item purpose/priority/unit/explicit-quantity validation on both create paths after client migration; historical unknown remains null. Keep permission classes explicit and create the full role × action × purchase relationship × API-key/anonymous test matrix. If key identity cannot be audited/scoped, block machine writes to new operations pending separately approved access changes.
4. **Verification:** migration rehearsal on PostgreSQL with existing rows; command, invalid-payload, rollback, version/concurrency, idempotency, allocated-item protection, and monetary invariants tests; check permission equivalence for existing routes; bounded-query tests; compare generated OpenAPI with prior contracts. Run applicable commands from [quality gates](../../../../../docs/ai-team/quality-gates.md) and perform an independent security/QA/code review. Do not merge/deploy before owner approval.

**Acceptance mapping (future implementation, not yet tested):** draft round-trip with several lines and distinct purposes; only draft/unallocated lines editable; stale update does not lose edits; existing historical/null data loads; old/read clients still operate until approved cutover; no planned line creates allocation, invoice, budget reservation, or cash event; API security, generated schema, and money reports retain their documented meanings.
