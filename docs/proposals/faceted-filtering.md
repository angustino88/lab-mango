# All-feature filtering and faceting plan

**Status:** Proposed, not an approved API contract. **Date:** 2026-11-05.
**Implementation risk:** T2 (new public API contracts, cross-feature rollout, and potentially sensitive counts).
**Scope:** Current Labs, Support Desk, Users, and notifications routes. No code, migrations, or deployed contracts are changed by this plan.

## Outcome and terminology

For every frontend collection that needs interactive filters, show valid dependent choices. Where the product needs *faceted search*, show choices (and optionally counts) based on the **same visible records matched by the current list filters**. Implement only dimensions that have a documented UI use case; “all filters” means every feature is assessed, not that every free-text field becomes a facet.

| Surface | Question it answers | Existing basis |
| --- | --- | --- |
| List filters | Which records should the list return? | Owner's validated list query and selector. |
| Filter metadata | Which parameters and fixed enum choices can the client send? | Existing `/filters` routes and `core/common/api/filtering.py`. |
| Catalog `/options` | Which reference-data IDs can a form select? | Existing bounded `{id, sku, name}` selector routes; may include unused catalog rows. |
| Result-set facets | Which values occur in the *currently matching, actor-visible records*, and how many? | **Not established as a common API contract.** Proposed per owner. |

Do not silently change `/options`, `/filters`, summary/report endpoints, or list responses into facets. Do not infer that an available catalog row is represented in inventory. Follow `docs/architecture/decisions/002-catalog-and-selector-api.md` for existing catalog/selector contracts. Its implementation-status prose may lag deployed routes; verify code and generated OpenAPI before editing the ADR.

## Proposed API design (requires human approval)

1. **Pilot one owner collection.** API Designer proposes a *new, additive, slashless sibling* facet endpoint only where the UI needs result-set choices. The exact route, query fields, response shape and limits are **not yet approved**. Existing list filters remain the source of truth; do not copy all filter parameters blindly if a dimension is unsafe or nonsensical.
2. **Reuse owner visibility.** An owner query builds the actor-authorized, non-deleted (where applicable), pre-pagination population used by its list. Apply validated search and remaining list filters to that population. Do not count from raw model managers or cross-owner private queries. Cross-feature behavior goes through `public.py` / `contracts.py`; `core.common` may host transport-only helpers, not business-model registries.
3. **Choose facet algebra explicitly:** AND between dimensions, OR for selected values within one multi-select dimension where that matches its list contract; decide whether a facet omits *its own* filter (disjunctive counts) or includes it (conjunctive counts). Specify null/unassigned buckets, zero-count values, retired selections, search effects, and equal outcomes for combined filters. No implicit coupling between lifecycle, booking, approval, assignment and activity statuses.
4. **Bound reads and disclose safely.** Counts mean distinct parent records, not joined rows, and do not depend on page or ordering. Cap returned bucket count; do not offer unbounded distinct free text, user IDs, prices or high-cardinality foreign keys. Avoid N+1 and full-table per-bucket queries; measure on representative data before adding indexes. Consider whether even a small count discloses protected records under the owner's permissions.
5. **Frontend behavior.** Fetch catalog `/options` for create/edit forms and use existing `include_ids` only to display previously selected retired values. Fetch facets only for approved list UIs; share the current validated search/filter state, debounce requests, discard stale responses, and retain a selected value when its count reaches zero according to the approved contract. Changing a catalog parent clears incompatible descendants; do not use the category string key where an integer `category_id` is required.
6. **Compatibility and errors.** New operation is potentially non-breaking; tightening previously accepted parameters, renaming list filters, changing `/options` meanings or changing deployed payloads is breaking and needs a separate approved migration plan. Unknown/repeated/invalid parameters follow the request standard (`400 invalid_query`); failures use the response-standard error envelope. Generate OpenAPI from code, never hand-edit generated files. Authentication and object-level authorization remain server-side.

## Staged delivery and acceptance criteria

| Stage | Work and owner | Acceptance evidence |
| --- | --- | --- |
| 0. Confirm scope | Engineering Lead + frontend owner inventory collection → accepted filter → UI control → selector/facet/none. | Signed-off matrix including non-applicable and sensitive surfaces, and decision whether counts are needed. |
| 1. Ship catalog wiring | Frontend owner integrates existing dependent `/options` chains; backend owner covers missing parent combinations with tests without silently tightening contracts. | Category → kind/type and category → manufacturer → `(manufacturer, type)` → model; geographic and vendor/product chains; wrong-parent and inactive/retired cases tested. |
| 2. Approve pilot design | API Designer + Architecture + Security + QA; Data Architect for measured query/index concerns. | Endpoint table, documented request/response and facet algebra, authorization matrix, bounded buckets, VER-2 compatibility classification, approved T2 brief. |
| 3. Implement pilot | Feature owner queries + thin API adapter; no generic ORM facet engine. | Facet bucket membership/count equals the *same authorized pre-pagination list population*; count test covers multi-select, unavailable options, joined-row duplicates, visibility, and page independence. |
| 4. Validate and review | QA, Security, independent reviewer. | Focused and wider tests, permission negatives/API-key scope, query budgets and representative execution plan, regenerated OpenAPI, schema lint, reviewer verdict. Record exact commands and outcomes. |
| 5. Expand per owner | Benches/rooms/stations/tickets; bookings/dashboard/license/finance only after specific scope/security decisions. | Each owner obtains a separate T2 brief, tests, OpenAPI and feature-doc update. No global behavior change by default. |

### Test checklist for each approved owner

- Compare each facet's returned IDs/counts with a distinct count over the actor-visible **filtered list before pagination**, including empty results and a later page.
- Verify AND across dimensions, OR within multi-select, own-filter inclusion/exclusion, search consistency, null buckets, retired selections, inactive catalog entries, wrong-parent pairs and hierarchical relations.
- Verify role/user/API-key/anonymous access and cross-scope negative cases; never reveal an otherwise hidden bucket via count or `include_ids`.
- Verify joins do not duplicate ticket/equipment buckets; verify time-sensitive booking/dashboard/monitoring filters against stable fixtures.
- Test `400` for unknown, repeated and malformed parameters; test cap behavior, stable order, response schema, generated documentation and authorized caching.
- Record query count and `EXPLAIN (ANALYZE, BUFFERS)` on representative PostgreSQL volume before proposing new indexes; test any approved schema migration and rollback separately.

## Decisions, limitations, and checks

**Human decisions required:** first pilot collection; collections actually used by the frontend; whether counts are required; conjunctive vs disjunctive count semantics; bucket limits; selected/zero/null behavior; actor/API-key visibility; authorization of financial, booking and user-derived counts. These cannot be inferred from existing `/options` routes.

**Facts vs proposals:** Declared routes, filter definitions, and relationships in the cited code are verified by inspection only. A shared result-set facet contract, its route and its response fields are proposals. Live data correctness, indexing adequacy, frontend usage and complete runtime/OpenAPI parity are **not verified**. Existing equipment catalog relations require no migration merely to build cascading dropdowns.

**Verification of this documentation-only change:** No Python code or API contract is changed; focused tests and OpenAPI regeneration are not required for this plan. Report repository status/diff checks separately if run. No check is “passed” without observed output. Implementation must follow `docs/ai-team/quality-gates.md`, update generated `openapi/` only when an API changes, and obtain T2 specialist and human approval before merge. Any later model change follows `docs/conventions/django-models.md` and updates the authoritative domain model documentation.
